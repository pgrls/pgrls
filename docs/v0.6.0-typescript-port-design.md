# v0.6.0 — TypeScript port of `pgrls.testing` (design doc)

**Status:** historical design doc. v0.6.0 shipped 2026-05-08 per
the design here; v0.6.1 polish landed 2026-05-12. Reading this
to understand the intent? Great. Reading this to implement a
third-language port? **Trust the shipped code over this doc** —
some details diverged during implementation. Specifically:

* The CI / package-layout snippets below assume a pnpm
  workspace at `ts/packages/testing/`. The shipped package is
  a single npm package at `ts/` (no monorepo). See
  [`ts/package.json`](../ts/package.json) and
  [`.github/workflows/ts.yml`](../.github/workflows/ts.yml) for
  what's actually wired.
* The starting version was bumped from 0.1.0 (in this doc) to
  0.6.0 during release coordination (TS package version tracks
  with the broader project milestone, not its own genesis).
* Conformance test paths are `ts/test/conformance/{pg,postgres-js}.conformance.test.ts`,
  not `ts/packages/testing/test/protocol.test.ts`.

Authored 2026-05-08.

## Goal

Ship a TypeScript / Node client that implements PROTOCOL_VERSION 1
(see `docs/pgrls-test-protocol.md`) so JS/TS shops can write the
same RLS tests they'd write in Python, against the same Postgres
schema, and trust the wire-level behaviour matches the Python
client byte-for-byte.

The lint / fix / snapshot / diff CLI subcommands are out of scope
for v0.6.0 — they stay Python. Only `pgrls.testing` ports.

## Motivation

JS/TS is the dominant stack for Supabase / Drizzle / Prisma /
Postgres.js shops, which is also where pgrls's RLS-testing story
lands hardest. Today those teams either:

* run pgrls.testing via a polyglot CI step (slow, awkward), or
* roll their own role-switching helpers (every team rolls their
  own, none get the savepoint nesting right).

A first-party TS port closes the second gap and removes the
polyglot friction of the first.

## Non-goals

* **Porting the lint / fix CLI.** That involves pglast (Python's
  Postgres AST library) and Z3 (SMT solver) — both have no
  drop-in TS equivalents. Re-implementing pglast in TS is a
  multi-quarter project on its own. Lint stays Python.
* **A pytest-equivalent fixture system.** Each test framework's
  fixture model is different; we provide the building blocks
  (per-test transaction, role-switch context manager) and let
  users wire them into their framework of choice. The Python
  client does the same thing — `PgrlsTestClient` is pure
  psycopg, the pytest fixture is a 65-line wrapper.

## Public API sketch

```ts
import { PgrlsTestClient } from 'pgrls-test';

// Open a connection (the client owns it) — ergonomic shape:
await using client = await PgrlsTestClient.connect(
  'postgres://test:test@localhost/test'
);

// Or wrap an existing pg.Client:
const client = new PgrlsTestClient(pgClient);

// Per-test transaction. Always rolls back at end.
await client.transaction(async () => {
  // Setup as the connecting (admin) role.
  await client.exec(
    'INSERT INTO app.documents (tenant_id, title) VALUES ($1, $2)',
    ['00000000-0000-0000-0000-000000000001', 'Tenant A doc']
  );

  // Switch role + claims.
  await client.asRole('app_authenticated', {
    claims: { sub: '00000000-0000-0000-0000-000000000001' },
  }, async () => {
    await client.assertVisible(
      'SELECT * FROM app.documents'
    );

    await client.assertRows(
      'SELECT * FROM app.documents',
      { count: 1 }
    );

    await client.assertRejected(
      "INSERT INTO app.documents (tenant_id) VALUES ('99999999-9999-9999-9999-999999999999')"
    );
  });

  // Nested role switches just work:
  await client.asRole('admin', {}, async () => {
    await client.assertVisible('SELECT * FROM app.documents');
  });
});
```

### Assertions (one-to-one with Python)

| TS method | Python method | Semantics |
|---|---|---|
| `assertRows(sql, { count })` | `assert_rows(sql, count=)` | Exactly N rows |
| `assertVisible(sql)` | `assert_visible(sql)` | At least 1 row |
| `assertInvisible(sql)` | `assert_invisible(sql)` | Zero rows |
| `assertRejected(sql)` | `assert_rejected(sql)` | Raises SQLSTATE 42501 |
| `assertSilentlyDropped(sql)` | `assert_silently_dropped(sql)` | UPDATE/DELETE … RETURNING → 0 rows |

Naming convention follows JS norms (camelCase) rather than mirroring
Python's snake_case — protocol invariants are language-neutral, but
the surface API is per-language idiomatic (per
`docs/pgrls-test-protocol.md`'s "out of contract" list).

### Seed helper

```ts
await client.seed('app.invoices', [
  { tenant_id: t1, amount_cents: 1234 },
  { tenant_id: t1, amount_cents: 5678 },
]);
```

Identifier handling mirrors Python: rightmost-`.`-split for
schema-qualified names, double-quoting via a TS port of
`pgrls.fixers._idents.quote_ident`. Same rejection of
multi-dot names ("cross-database refs unsupported").

## Architecture

### Package layout

Single npm package `pgrls-test`. No monorepo / workspace —
the surface stays small enough that one package is right.

```
ts/
  src/
    client.ts          # PgrlsTestClient
    assertions.ts      # raw assertion functions
    errors.ts          # PgrlsTestError, PgrlsTestAssertionError
    idents.ts          # quote_ident port
    drivers/
      types.ts         # Driver interface
      pg.ts            # pgDriver(client: pg.Client)
      postgres-js.ts   # postgresJsDriver(sql: postgres.Sql)
    index.ts           # public re-exports + PROTOCOL_VERSION
  test/
    client.test.ts     # vitest unit tests (mock driver)
    protocol-pg.test.ts        # protocol conformance via pg
    protocol-postgres-js.test.ts  # protocol conformance via postgres.js
  package.json         # pgrls-test
  tsconfig.json
  vitest.config.ts
  .eslintrc.cjs
```

The TS code lives **in the same repo** as the Python code (under
`ts/`). One repo, one source of truth for the protocol doc, one
PR for any cross-language behavioural changes. Releases are
independent: `pgrls` to PyPI, `pgrls-test` to npm.

### Postgres driver choice

**Both `pg` and `postgres.js` ship in v0.6.0.** Per Q2's
resolution, the package supports both drivers via a thin
adapter layer behind a `Driver` interface that exposes
`exec / fetchall / begin / commit / rollback / savepoint /
release / rollbackTo`.

```ts
import { Client } from 'pg';
import postgres from 'postgres';
import { PgrlsTestClient, pgDriver, postgresJsDriver } from 'pgrls-test';

// pg client:
const pgClient = new Client({ connectionString: url });
await pgClient.connect();
const c1 = new PgrlsTestClient(pgDriver(pgClient));

// postgres.js:
const sql = postgres(url);
const c2 = new PgrlsTestClient(postgresJsDriver(sql));
```

Both `pg` and `postgres` are **peer dependencies** with optional
flag — users install only the driver they actually use. No
duplicate copies in `node_modules`.

Why both:

* **`pg`** — mature, ubiquitous, used by Drizzle / Prisma /
  Postgres.js's fallback path. Most projects already have it
  transitively. Native savepoint support via `Client`.
* **`postgres.js`** — faster on benchmark workloads, no prepared-
  statement cache pollution, common in modern Supabase /
  Drizzle-on-postgres-js stacks. Tagged-template API requires
  using the `sql.unsafe(...)` escape hatch internally for our
  raw-SQL-with-params shape, but the abstraction hides that.

### Async model

All public methods return `Promise<T>`. No callback-style API.
Use modern `async`/`await` throughout. The Python client uses
sync psycopg; the TS port uses async pg. The protocol doesn't
care.

The `transaction` and `asRole` methods take an async callback
rather than returning an `await using` resource. Reasoning: the
callback shape makes the rollback / RELEASE SAVEPOINT point
unambiguous in the source code, matches Python's `with`
contextmanager style, and `await using` doesn't cleanly forward
exceptions through the disposer in the way we need to flip
between RELEASE and ROLLBACK based on the success/failure path.

### Identifier quoting (`idents.ts`)

Port from `src/pgrls/fixers/_idents.py`. Port the round-trip
test at `tests/test_idents.py` byte-for-byte to TS so any
divergence is caught immediately. Re-implementation, not FFI —
the function is ~30 lines of regex + string ops; not worth
shelling to Python.

### Error hierarchy

```ts
export class PgrlsTestError extends Error { /* ... */ }
export class PgrlsTestAssertionError extends PgrlsTestError {
  // Subclasses for Vitest's diff display? Keep flat for now;
  // Vitest matches by name + message pattern.
}
export class PgrlsTestConfigError extends PgrlsTestError { /* ... */ }
```

`PgrlsTestAssertionError` deliberately does NOT extend `AssertionError`
(Node's built-in) — that has special semantics in jest/vitest
that include a `diff` shape we don't produce. Better to be a
plain Error subclass that vitest's default error renderer handles
correctly.

## Test framework integration

### Vitest (first-class)

```ts
// vitest.setup.ts
import { afterAll, beforeAll, beforeEach } from 'vitest';
import { Client } from 'pg';
import { PgrlsTestClient } from 'pgrls-test';

let pgClient: Client;
let pgrls: PgrlsTestClient;

beforeAll(async () => {
  pgClient = new Client({ connectionString: process.env.DATABASE_URL });
  await pgClient.connect();
  pgrls = new PgrlsTestClient(pgClient);
});

afterAll(async () => {
  await pgClient.end();
});

beforeEach(async (ctx) => {
  // Stash on context so tests can grab it.
  (ctx as any).pgrls = pgrls;
});
```

Documented as a recipe in the README. Jest / node:test get
similar recipes; no first-class plugin like the pytest plugin.

### `pgrls_db`-equivalent fixture? Skipped for v0.6.0.

Pytest's plugin discovery is much tighter than vitest's — the
Python plugin is a 65-line module with `@pytest.fixture`. The TS
equivalent (a vitest setup file) is so thin that shipping it as
a separate package adds friction (one more dep, one more
lockstep version) without commensurate value. Defer to v0.7.0
if user feedback demands it.

## Conformance test strategy

The **same** test suite runs against both clients. Concretely:

```
docs/pgrls-test-protocol.md → conformance test corpus

ts/packages/testing/test/protocol.test.ts:
  - implements the conformance criteria from the protocol doc
  - runs against a real Postgres testcontainer
  - asserts all four conformance points

src/pgrls/testing/test_protocol.py:
  - mirror of the above, in Python
  - same Postgres state, same assertions
  - already partially exists in tests/testing/
```

A new dev-only CI job (`conformance-cross-lang`) starts one
Postgres testcontainer and runs both suites against it,
asserting they observe the same end-state. Catches the case
where one client wires a primitive subtly wrong and only its
language's tests pass.

## Versioning + release coordination

* `pgrls-test` follows its own SemVer track: starts at 0.1.0
  with PROTOCOL_VERSION = 1.
* Bump the npm package's MINOR when adding non-breaking helpers.
* PROTOCOL_VERSION bumps require a coordinated release of both
  `pgrls` (Python, MAJOR or MINOR depending on Python-side
  breakage) and `pgrls-test` (TS, MAJOR — the protocol
  contract is the public surface).
* The protocol doc carries the canonical version number; both
  clients import it as a constant and assert at construction.

Add to the existing `pytest pg17` matrix as a parallel job, not

## Development workflow

* Local dev: `pnpm -C ts install` (one-time), then
  `pnpm -C ts/packages/testing test --watch` for iteration.
* Postgres available via `docker compose up -d postgres` (a new
  `ts/docker-compose.yml` mirrors `demo/docker-compose.yml` —
  same image, different host port to avoid clashes).
* Type-check: `pnpm -C ts/packages/testing typecheck` (strict
  TS settings, `strict: true` in `tsconfig.json`).
* Lint: ESLint + Prettier with `@typescript-eslint`. Match
  ruff's "be reasonable, don't bikeshed" style.

## Migration / adoption story

Day-one users get a recipe-driven docs page (TS-side) showing
the vitest setup and a side-by-side equivalence with the Python
client. The cross-language conformance section anchors the trust
story: "the same SQL ran, the same SQLSTATE came back, in both
languages."

## Resolved decisions (2026-05-08)

The four open questions below were resolved before
implementation began. Recording the answers here so future
readers see the design as actually shipped, not the pre-
decision draft.

1. **Package name.** ✅ **`pgrls-test` (unscoped).** One fewer
   character to type, no scope to pre-register. If a future
   `@pgrls/cli` or `@pgrls/types` materializes we can rename
   then; for now the un-namespaced single package keeps the
   public surface flat.

2. **`postgres.js` adapter.** ✅ **Ship in v0.6.0.** Both `pg`
   and `postgres.js` adapters land together in the initial
   release. Driver layer is a thin abstraction over "execute
   SQL", "begin / commit / rollback", "savepoint /
   release / rollback to" — small enough to support two
   drivers without forcing a heavyweight plugin system.
   Bumps the effort estimate by ~1.5 person-days vs the
   pg-only original.

3. **Drizzle / Prisma examples.** Drizzle's transaction API
   could wrap our transaction. Prisma's connection pool model
   is more constrained — `$transaction` returns a different
   client per call which complicates `as_role`'s "capture
   state on this connection" semantics. Ship Drizzle recipe;
   defer Prisma to a contributed recipe.

4. **JSR vs npm.** ✅ **npm only.** JSR is a five-line
   addition once the npm package stabilizes. v0.6.x can add
   it without a major bump.

5. **ESM only or CJS+ESM?** ✅ **ESM-only.** Vitest (the
   primary target) is ESM-native; modern Node (≥20 LTS) is
   ESM-first; the audience for a *test-time* library
   already runs modern toolchains. CJS-only stacks (rare in
   2026) can wait for a 0.6.x dual-publish if demand
   materializes.

## Decision log

* **Same repo, separate package.** Single source of truth for
  the protocol; independent releases.
* **Both `pg` and `postgres.js` drivers in v0.6.0.** Two
  thin adapters over the same `Driver` interface. Users pick
  via construction, e.g.
  `new PgrlsTestClient(pgClient)` vs
  `new PgrlsTestClient(sqlClient)`.
* **Callback-shaped `transaction` / `asRole`.** Mirrors Python's
  contextmanager API; cleaner exception flow than `await using`
  + Symbol.asyncDispose for a method that needs to branch on
  success vs failure.
* **No first-class test-framework plugin in v0.6.0.** Recipes
  beat plugins until plugin demand materializes.
* **`pgrls-test` unscoped.** Simpler than a `@pgrls/*` scope;
  no scope pre-registration; rename later if a multi-package
  surface emerges.
* **ESM-only.** Vitest is ESM-native; modern Node is ESM-first;
  audience runs modern toolchains.
* **npm only.** JSR is a v0.6.x add.
